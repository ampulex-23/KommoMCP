## Вопрос 4: Прочитайте лог

**HTTP-статус 200, но Error: 1010 — это нормально?**
Да, это распространённая практика. Многие API (особенно legacy и CRM-системы) используют HTTP 200 для всех ответов, а бизнес-ошибки передают в теле ответа через собственные коды. Это позволяет отличить «сервер работает, но запрос некорректен» от «сервер упал». HTTP-статус говорит о транспорте, Error в теле — о бизнес-логике.

**Что означает код 1010?**
Без документации точно не скажу, но по контексту (пустой Parameters) — скорее всего это ошибка авторизации, истёкший токен, или запрос с невалидными/отсутствующими обязательными параметрами. Возможно также — клиент не найден или метод недоступен для данного аккаунта.

**Что бы сделал по-другому:**
1. Не показывать пользователю общее «Произошла ошибка» — нужно парсить код ошибки и давать конкретное сообщение (например, «Не удалось найти ваш профиль» или «Сервис временно недоступен»).
2. Завести маппинг известных кодов ошибок → человекочитаемых сообщений.
3. Логировать Request_id для быстрой отладки с командой API.
4. Если ошибка повторяемая (например, 1010 = невалидный токен) — реализовать автоматический retry с обновлением токена, а не просить пользователя «попробовать позже».

## Вопрос 5: Цепочка API-вызовов

Клиент: «Запиши меня на йогу завтра на 18:00»

**Шаг 1: getClientByPhone**
- Параметры: Phone (номер телефона клиента, берём из WhatsApp-профиля)
- Получаем: ClientID
- Зачем: идентифицировать клиента в системе
- Что может пойти не так: клиент не найден (нет в базе) → предложить зарегистрироваться или уточнить номер

**Шаг 2: getSchedule**
- Параметры: StartDate = завтрашняя дата 00:00, EndDate = завтрашняя дата 23:59
- Получаем: список занятий с ID, названием, временем, типом, свободными местами
- Зачем: найти занятие «Йога» в 18:00
- Что может пойти не так: нет занятий йогой завтра, нет занятий в 18:00, несколько занятий йогой в 18:00 (разные залы/тренеры) → показать варианты и уточнить

**Шаг 3: Проверка свободных мест**
- Из ответа getSchedule смотрим AvailableSlots для найденного занятия
- Что может пойти не так: AvailableSlots = 0 → сообщить что мест нет, предложить другое время или лист ожидания

**Шаг 4: getClientAppointments**
- Параметры: ClientID
- Получаем: список текущих записей клиента
- Зачем: проверить что клиент не записан уже на это занятие, и нет пересечений по времени
- Что может пойти не так: клиент уже записан → сообщить об этом

**Шаг 5: Определяем тип занятия**
- Из getSchedule берём Type: Group или Personal
- Если Group → используем SetGroupAppointment
- Если Personal → нужны getAvailableTrainers → getAvailableDates → getAvailableTimes → setAppointment

**Шаг 6 (для группового): SetGroupAppointment**
- Параметры: ClientID, AppointmentID (ID занятия из getSchedule)
- Получаем: подтверждение записи
- Что может пойти не так: место заняли пока шёл диалог (race condition), нет активного абонемента, ошибка API

**Шаг 7 (опционально): getTickets**
- Параметры: ClientID
- Зачем: проверить что у клиента есть действующий абонемент/членство, покрывающее это занятие
- Лучше вызвать до записи (между шагом 4 и 6), чтобы не получить ошибку при записи
- Что может пойти не так: абонемент истёк, не покрывает данный тип занятий

## Вопрос 6: GPT и LLM

### 6А. Неверное утверждение

**Номер: 2**

**Почему:** function calling НЕ позволяет модели вызывать внешние API напрямую. Модель лишь генерирует JSON с именем функции и параметрами — это структурированный «запрос на вызов». Фактический вызов API выполняет наш код (оркестратор), который получает этот JSON, делает HTTP-запрос, и передаёт результат обратно модели. GPT не имеет доступа к сети и не может сама ничего вызвать.

### 6Б. Нестабильная работа LLM

В проекте KommoMCP бот на gpt-4o при удалении кастомных полей сообщал пользователю «42 поля удалено, 19 не удалось» — но при повторном запросе списка все поля оставались на месте. Проблема: API возвращал HTTP 200 на DELETE системных полей (tracking_data), но фактически не удалял их. Модель видела в ответе `deleted: 42, failed: 19` и интерпретировала это как успех, хотя «deleted» включало и те поля, что API молча проигнорировал.

Что помогло: 1) Добавил фильтрацию системных полей (tracking_data, PHONE, EMAIL, WEB, ADDRESS, POSITION, IM) на уровне кода — они пропускаются и не считаются в deleted. 2) Возвращаю модели чёткий отчёт с разделением: `deleted_names`, `skipped_system`, `failed` — модель больше не может неправильно интерпретировать результат. 3) Поднял модель до gpt-5-mini для лучшего следования инструкциям.

## Вопрос 7: Два интента в одном сообщении

**Какие функции должен вызвать роутер?**
Две: `schedule` (расписание на завтра после обеда) и `cancel` (отмена утренней йоги).

**Если модель может вызвать только одну функцию за раз — как обработать?**
Решение: после выполнения первой функции и получения результата — вернуть управление роутеру с оставшейся частью запроса. Конкретно:
1. Роутер вызывает первую функцию (например, `cancel` — она критичнее).
2. После завершения отмены, оркестратор проверяет: остались ли необработанные интенты? Если да — снова вызывает роутер с оставшимся контекстом.
3. Альтернативный подход: роутер возвращает массив интентов с приоритетами, оркестратор выполняет их последовательно.

**Описание функции schedule (чтобы не путать с book):**
«Возвращает расписание занятий на указанный период. Только просмотр — НЕ записывает клиента. Используй когда клиент хочет узнать какие занятия есть, посмотреть расписание, спрашивает что доступно.»

## Вопрос 8: System prompt — сравнение

**Какой вариант лучше для production?**
Вариант Б.

**3 конкретные проблемы варианта А:**
1. **Галлюцинации**: нет запрета выдумывать данные — бот будет придумывать названия занятий, тренеров и расписание из своих обучающих данных вместо вызова API.
2. **Нет управления состоянием**: без params бот не помнит на каком шаге диалога находится — при многошаговой записи (выбор даты → выбор занятия → подтверждение) будет терять контекст или перескакивать шаги.
3. **Нет граничных условий**: не описано что делать когда мест нет, когда несколько занятий с одним названием, когда клиент не указал дату — бот будет принимать решения сам, непредсказуемо (например, подставит сегодняшнюю дату без спроса).

**Зачем строка «Продолжай строго с объектом params. Не создавай новый»?**
LLM склонна «обнулять» состояние между вызовами — вместо продолжения существующего объекта params она может создать новый с дефолтными значениями, потеряв всё что клиент уже выбрал (дату, занятие, тренера). Эта инструкция заставляет модель работать с переданным состоянием как с мутабельным объектом, а не пересоздавать его.

## Вопрос 9: Галлюцинации и достоверность

**Почему бот мог так ответить?**
GPT обучена на огромном корпусе текстов, включая описания фитнес-клубов, расписания, имена тренеров. Когда модель не вызвала инструмент getSchedule, она сгенерировала правдоподобный ответ из своих обучающих данных — «Hot Yoga», «тренер Алексей», «19:30» звучат реалистично. Модель оптимизирована быть полезной и давать ответ, даже если данных нет — это и есть галлюцинация.

**3 приёма чтобы предотвратить:**
1. **В промпте**: явный запрет — «НИКОГДА не называй занятия, тренеров, время или цены, если ты не получил эти данные из инструмента. Если данных нет — скажи что нужно проверить и вызови инструмент.»
2. **В архитектуре**: сделать вызов getSchedule обязательным шагом в пайплайне до ответа пользователю — не давать агенту возможность ответить про расписание без предварительного вызова API. Например, через checkConditions: если ответ содержит время/название занятия, но getSchedule не вызывался → блокировать ответ.
3. **В коде**: валидация ответа — перед отправкой пользователю проверять что упомянутые ID занятий, имена тренеров и время реально существуют в последнем ответе API. Если нет — перезапросить у модели.

**«Не выдумывай» vs «не давать данные без инструмента» — что надёжнее?**
Второй подход надёжнее. Инструкция «не выдумывай» — это soft constraint, модель может её нарушить (особенно при длинных диалогах, когда инструкция «размывается»). А архитектурное ограничение — hard constraint: если данные физически не попадают в контекст модели без вызова инструмента, она не сможет их выдумать в правильном формате. Промпт — это пожелание, архитектура — это гарантия.

## Вопрос 10: Дебаг нестабильной работы

**Где искать причину (3+ гипотезы):**

1. **Общий контекст между сессиями**: если conversation history не изолирована по пользователям — ID занятий из предыдущего разговора с другим клиентом попадают в контекст текущего. Это прямо подтверждается логами («иногда бот использует ID из предыдущего разговора с другим клиентом»).

2. **Кэширование ответа getSchedule**: если результат getSchedule кэшируется и не обновляется между сессиями — бот может использовать устаревшие ID.

3. **Промпт не привязывает ID к конкретному выбору**: модель видит список занятий, клиент говорит «второе» или «йогу в 18:00», и модель неправильно матчит текстовый выбор с ID из списка.

4. **Race condition**: между показом расписания и записью прошло время, расписание обновилось, ID сместились.

**Самая вероятная гипотеза:**
Гипотеза 1 — общий/протекающий контекст. Логи прямо говорят что бот берёт ID из разговора с другим клиентом. Это значит что conversation history либо глобальная, либо неправильно очищается между сессиями. 70/30 соотношение объясняется тем, что в большинстве случаев ID совпадают (популярные занятия), но когда предыдущий клиент спрашивал про другое — ID «протекает».

**Как исправить:**
1. Изолировать conversation history строго по user_id/chat_id — каждый клиент видит только свой контекст.
2. Очищать контекст при начале нового сценария записи.
3. Добавить валидацию: перед вызовом SetGroupAppointment проверять что AppointmentID существует в последнем ответе getSchedule для ЭТОГО пользователя.
4. В промпте явно указать: «Используй ТОЛЬКО ID занятий из последнего вызова getSchedule. Никогда не используй ID из предыдущих разговоров.»

## Вопрос 11: RAG — когда нужен и когда нет

| Источник данных | Способ | Почему |
|----------------|--------|--------|
| **Расписание занятий** | **API** | Обновляется ежедневно, нужны актуальные данные в реальном времени. Кэш в промпте или RAG устареет за часы. Бот должен вызывать getSchedule при каждом запросе. |
| **Прайс-лист** | **System prompt** | 10 позиций — это ~200-300 токенов, легко помещается в промпт. Обновляется раз в полгода — нет смысла усложнять архитектуру. При изменении — обновить промпт. |
| **FAQ (50 вопросов)** | **RAG** | 50 Q&A — это слишком много для промпта (~5000+ токенов, засорит контекст). Но и API не нужен — данные статичные. RAG найдёт 2-3 релевантных ответа по запросу и подставит только их. |
| **Информация о тренерах** | **RAG** | 15 тренеров × 2-3 абзаца = ~3000-4500 токенов. В промпт не влезет без потери качества. RAG подтянет инфу только о тренере, про которого спрашивают. Обновляется редко — не нужен API. |

### 12В

**1. Зачем filter → save_variables перед agent?**
Два промежуточных шага нужны чтобы: (а) filter убирает нерелевантные данные — из 100 занятий оставляет только групповые с местами на нужную дату, иначе агент получит огромный JSON и может запутаться или превысить контекст; (б) save_variables форматирует сырой JSON в читаемый текст/структуру для агента — вместо `{"ID": 1, "Service": {"Title": "Йога"}, "StartDate": "2026-02-11T09:00:00", "AvailableSlots": 3}` агент получит «Йога — 09:00 (3 места)». Это экономит токены и снижает вероятность ошибки.

**2. Зачем runScenario?**
DRY-принцип: одна и та же цепочка (api → filter → save_variables) нужна и в ветке «расписание» и в ветке «записаться». Без подсценария пришлось бы дублировать 3 ноды. При изменении логики фильтрации (например, добавить фильтр по абонементу) — правишь в одном месте, а не в двух. Также упрощает тестирование — можно протестировать подсценарий изолированно.

**3. Что проверяет checkConditions после SetAppointment?**
Проверяет поле Error в ответе API. Ветки:
- **Error = 0 (успех)** → getResult с сообщением «Вы записаны на [занятие] в [время]» + кнопка «Отменить запись»
- **Error ≠ 0 (ошибка)** → дальше может быть ещё одно ветвление по коду ошибки: нет мест → предложить другое время; нет абонемента → предложить купить; клиент уже записан → сообщить об этом; другая ошибка → «Не удалось записать, попробуйте позже» + логирование

## Вопрос 13: JSON и код

**Какой вариант надёжнее?**
Вариант Б.

**Что делает regex `/^[1-9]\d{10,14}$/`?**
Проверяет что строка — это валидный номер телефона: начинается с цифры 1-9 (не с нуля), далее от 10 до 14 цифр. Итого 11-15 цифр — покрывает форматы от российских (79001234567, 11 цифр) до международных (до 15 цифр по стандарту E.164).

**Что делает `.replace(/\D/g, '')`?**
Удаляет все нецифровые символы из строки. `\D` — любой символ кроме цифры, `g` — глобально (все вхождения). Превращает `+7 (900) 123-45-67` в `79001234567`.

**Пример сообщения где А сохранит мусор, а Б — корректный номер:**
Пользователь пишет: `Мой номер +7 (900) 123-45-67, запишите меня`
- Вариант А сохранит: `Мой номер +7 (900) 123-45-67, запишите меня` — весь текст сообщения как «телефон»
- Вариант Б: очистит от нецифровых символов → `79001234567`, проверит regex → валидный номер, сохранит `79001234567`

**Что делаю первым делом?**

**Как организую информацию?**
Таблица в Google Sheets / Notion, расшаренная с командой и клиентом:

|-------|--------|----------|---------------------|

## Вопрос 17: Архитектура

Запись выполняет **наш код**, не GPT. GPT не имеет доступа к сети и не может вызывать API напрямую. Когда клиент пишет «запиши меня на йогу», GPT анализирует запрос и генерирует структурированный JSON через function calling — например, `{"name": "SetGroupAppointment", "arguments": {"ClientID": 123, "AppointmentID": 456}}`. Наш код-оркестратор получает этот JSON, выполняет реальный HTTP-запрос к API фитнес-клуба, получает ответ, и передаёт результат обратно GPT — которая уже формулирует человекочитаемый ответ клиенту.
